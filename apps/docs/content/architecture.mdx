# معماری سیستم

## ساختار Monorepo

پروژه در قالب یک monorepo (با npm workspaces) سازمان‌دهی شده تا فرانت‌اند/بک‌اند/مستندات مستقل توسعه یابند اما به‌صورت یکپارچه دیپلوی شوند:

```text
/
├── apps/
│   ├── web/     ← اپ اصلی Next.js (App Router)
│   │             شامل PWA کارگری آفلاین-اول + API بک‌اند (app/api) + داشبورد مالک (app/owner)
│   └── docs/    ← همین سایت مستندات (Nextra)
└── legacy/
    └── farm-windows.html   ← نمونه اولیه‌ی تک‌فایلی، به‌عنوان مرجع تاریخی نگه‌داری شده
```

چرا فرانت‌اند و بک‌اند در یک اپ Next.js؟ چون Route Handlerهای App Router (`app/api/**/route.ts`) دقیقاً همان نقش یک بک‌اند اختصاصی را ایفا می‌کنند، بدون نیاز به یک سرویس مجزا و بدون پیچیدگی CORS/دیپلوی دوگانه. کد بک‌اند (`app/api/`, `prisma/`, بخش‌هایی از `lib/`) از کد فرانت‌اند کارگری (`app/(worker)/`) به‌وضوح در پوشه‌های جدا نگه‌داری می‌شود.

## پشته‌ی فناوری

| لایه | فناوری |
| --- | --- |
| فرانت‌اند | Next.js (App Router) + React + TypeScript + Tailwind CSS v4 |
| ذخیره‌سازی محلی/آفلاین | Dexie.js (روی IndexedDB) |
| مدیریت وضعیت | Zustand |
| بک‌اند | Next.js Route Handlers |
| ORM / دیتابیس | Prisma + PostgreSQL (پیشنهادی: [Neon](https://neon.tech)) |
| احراز هویت مالک | JWT امضاشده در کوکی HttpOnly (کتابخانه‌ی `jose`) |
| نمودارهای داشبورد | Recharts |
| مستندات | Nextra |

## جریان همگام‌سازی آفلاین-اول

1. کاربر یک فرم را ثبت/ویرایش می‌کند → رکورد بلافاصله در **IndexedDB** (روی همان دستگاه) ذخیره می‌شود، با پرچم `synced: false`.
2. اگر دستگاه آنلاین باشد، بلافاصله یک درخواست `POST /api/sync/[module]` با همان رکورد (شامل `uid` یکتا) به بک‌اند ارسال می‌شود.
3. بک‌اند رکورد را بر اساس `uid` در PostgreSQL **upsert** می‌کند و پاسخ موفق برمی‌گرداند → رکورد محلی به `synced: true` تغییر می‌کند.
4. اگر دستگاه آفلاین باشد (یا درخواست شکست بخورد)، رکورد همان‌طور با `synced: false` در IndexedDB باقی می‌ماند — هیچ داده‌ای پاک نمی‌شود.
5. به‌محض اتصال مجدد اینترنت (رویداد `online` مرورگر) یا هر ۶۰ ثانیه به‌عنوان یک بررسی ایمنی، همه‌ی رکوردهای `synced: false` دوباره ارسال می‌شوند.
6. حتی بازِ کردن مجدد اپ در حالت کاملاً آفلاین هم کار می‌کند: Service Worker پوسته‌ی اپ را از کش قبلی برمی‌گرداند (بخش [PWA و کارکرد آفلاین](#pwa-و-کارکرد-آفلاین)).

نکته‌ی کلیدی: چون هر رکورد یک `uid` یکتا (تولیدشده در سمت کاربر) دارد، ارسال دوباره‌ی یک رکورد (مثلاً به‌خاطر قطع و وصل شدن پیاپی اینترنت) هرگز باعث تکرار رکورد در دیتابیس نمی‌شود — سرور همیشه یک `upsert` بر اساس `uid` انجام می‌دهد.

## مدل داده (خلاصه)

هر یک از ۱۰ دفتر عملیاتی (`Attendance`, `Machinery`, `Irrigation`, `PestFertilizer`, `Orchard`, `Inventory`, `Accounting`, `Harvest`, `Sheep`, `Security`) یک مدل Prisma مستقل با فیلد `uid` یکتا دارد. شِمای کامل در `apps/web/prisma/schema.prisma` قرار دارد.

## داشبورد مالک

مسیر `/owner` پشت یک لایه‌ی احراز هویت مستقل قرار دارد:

1. مالک با ایمیل/رمز عبور در `/owner/login` وارد می‌شود.
2. یک JWT امضاشده در یک کوکی `httpOnly` ذخیره می‌شود.
3. Layout محافظت‌شده‌ی `/owner/(dashboard)` این کوکی را در سمت سرور بررسی می‌کند و در صورت نامعتبر بودن، کاربر را به صفحه‌ی ورود هدایت می‌کند.
4. صفحه‌ی داشبورد با کوئری‌های تجمیعی Prisma (در سمت سرور) داده‌های نمودارها را می‌سازد و به یک کامپوننت Recharts سمت کلاینت می‌فرستد.

## PWA و کارکرد آفلاین

- یک [`manifest.webmanifest`](/) تولیدشده (`app/manifest.ts`) امکان نصب روی صفحه‌ی اصلی گوشی را فراهم می‌کند.
- یک Service Worker دستی (`public/sw.js`) با راهبرد «شبکه اول، سپس کش» برای صفحات و «کش اول» برای فایل‌های استاتیک، باعث می‌شود پوسته‌ی اپ حتی در بی‌سیمی کامل هم بالا بیاید — نه فقط داده‌ها، بلکه خودِ صفحه.
